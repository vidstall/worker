# Golden VM Image — dvconf relay-saturation / WAN / demo bring-up (baked 2026-07-10)

A **reusable dependency-ready Azure VM image** baked from the `rms-r3-overlap` VM so future
relay-saturation / WAN-latency / live-demo bring-ups **SKIP the ~30-min heavy bootstrap**
(apt toolchain + **mediasoup-worker native C++ build** + ~786 MB sui download + `pnpm install`
+ playwright chromium download). Spin a dep-ready VM in **koreacentral OR japaneast** with a
single `az vm create --image <id>`.

> Baked from the generalized `rms-r3-overlap` (RG `dvconf-rms-e2ee`, japaneast) on **2026-07-10**.
> Source VM was **DESTROYED** (deprovisioned + generalized) with explicit user approval — a
> generalized VM cannot be restarted; it lives on only as this image. The other 5 rms-* VMs
> were left running and untouched.

## 2. Bring-up from golden — `az vm create` (git-bash / WSL)

```bash
# ---- pick a region: koreacentral OR japaneast (SIG version is replicated to both) ----
REGION=koreacentral                       # or: japaneast
RG=dvconf-rms-<run>                        # your ephemeral run RG (create it first)
VM=rms-<role>                              # e.g. rms-r1-primary
IMG=/subscriptions/fe499113-8f65-4b58-a633-1e015b82afef/resourceGroups/dvconf-golden-rg/providers/Microsoft.Compute/galleries/dvconfGallery/images/dvconf-rms-golden

az group create -n "$RG" -l "$REGION"      # once per run

az vm create \
  --resource-group "$RG" \
  --name "$VM" \
  --location "$REGION" \
  --image "$IMG" \
  --size Standard_B2s_v2 \
  --admin-username azureuser \
  --ssh-key-values ~/.ssh/dvconf_deploy.pub \
  --public-ip-sku Standard \
  --output json

# capture IP
VM_IP=$(az vm show -g "$RG" -n "$VM" --show-details --query publicIps -o tsv)
echo "VM_IP=$VM_IP"
```

> **Security type must stay Standard.** The definition has NO SecurityType feature, matching the
> Standard-security Gen2 source. Do NOT add `--security-type TrustedLaunch` — it would mismatch.
> Size `Standard_B2s_v2` matches what the image was baked/proven on (2 vCPU).

> **japaneast-only fallback** (managed image): swap `--image` for
> `/subscriptions/fe499113-8f65-4b58-a633-1e015b82afef/resourceGroups/dvconf-golden-rg/providers/Microsoft.Compute/images/dvconf-rms-golden-2026-07-10`
> (only works with `--location japaneast`).

### SSH in
```bash
ssh -i ~/.ssh/dvconf_deploy azureuser@$VM_IP      # git-bash key: /c/Users/<you>/.ssh/dvconf_deploy
```
The `azureuser` account + host keys are freshly regenerated by cloud-init on first boot (the
image was `waagent -deprovision+user`'d, so it carries no stale identity). Just re-supply your
public key via `--ssh-key-values` as above.

## 3. What is PRE-BAKED vs what each role still needs per run

### Pre-baked into the image (verified 2026-07-10 before generalize)

- **OS**: Ubuntu 22.04 LTS (jammy), Gen2. Full apt build toolchain already installed (the
  mediasoup-worker native build prerequisites).
- **node** v20.20.2, **pnpm** 10.30.3 (corepack-pinned).
- **`~/dvconf-daemons`** repo @ `e99f0e6` (branch `feat/relay-saturation-internet-bench`)
  - `node_modules` present (187 MB)
  - **`mediasoup-worker` BUILT** — the expensive ~10-min native C++ compile is DONE
    (`node_modules/.pnpm/mediasoup@3.19.17/.../worker/out/Release/mediasoup-worker`, 9.8 MB).
- **`~/dvconf-client`** repo @ `d7a622c` (branch `feat/relay-saturation-internet-bench`,
  `packageManager` pinned `pnpm@10.30.3`)
  - `node_modules` present (208 MB, `pnpm install --frozen-lockfile`)
- **Playwright chromium** installed with system deps: `~/.cache/ms-playwright/chromium-1228`
  + `chromium_headless_shell-1228` + `ffmpeg-1011` (headless bench browser for consumer VMs).
- **ufw** was configured on r3 with relay ports (4000/4001/8080/8081/9000 + UDP 40000-49999).
  NOTE: cloud-init may reset the hostname/firewall on the new VM — re-assert ufw + your run's
  actual ports from the runbook if needed. The NSG (Azure-side firewall) is per-run anyway and
  is NOT part of the image — create NSG rules per `azure-wan-runbook.md`.

> **Consumer extras WERE added** — this is a **UNIVERSAL** image serving ALL roles
> (relay / committee-minus-sui / consumer). The client repo + playwright chromium (the
> consumer-only extras that originally lived only on the 2 consumer VMs) were installed onto
> r3 before baking, so a consumer VM from this image needs **no** extra `playwright install` or
> client clone.

### NOT baked — `sui` binary (important)

`rms-r3-overlap` was a **relay-only** VM and **never had the `sui` CLI** (only the committee VM
ran the localnet chain). So the golden image does **NOT** contain `sui`. Any VM that must run the
Sui localnet / publish Move / register on-chain (i.e. the **committee** role) still needs sui
installed per run:

```bash
# on a committee VM from this image (~786 MB download + ~1-2 min):
# install sui 1.66.2 (mainnet-v1.66.2) — see azure-wan-runbook.md / prior bootstrap for the exact
# release URL; e.g. via suiup or the GitHub release tarball, then `sui --version` to confirm.
```

### INHERENT per-run (the image physically cannot bake these — localnet is ephemeral)

Every fresh run must still do these on the committee VM (they produce run-specific on-chain
object IDs / keys that only exist for that localnet instance):

1. `sui start --force-regenesis` (fresh ephemeral localnet — new chain-id each time).
2. **Publish the Move package** → new `PACKAGE_ID` + 10 registry object IDs.
3. **Register on-chain identities**: CP, signaling, 4 validators, and the **3 distinct relays**
   (fund each ~999 SUI), seed `QuorumConfigState`, etc.
4. Distribute the fresh `chain-config.env` (object IDs + relay keys + `INTER_RELAY_TOKEN`) to the
   relay/consumer VMs.

Do NOT reboot the committee VM mid-run — the localnet chain is in-memory/ephemeral and a reboot
loses the chain-id. (This is unchanged from the existing runbooks; the golden image only removes
the toolchain/build/deps setup time, not the per-run chain genesis.)

### Also refresh per run (code moves fast)

The baked repos are pinned at the commits above. If the run needs newer code, `git pull` (or
deliver a fresh git bundle + `pnpm install --frozen-lockfile`) inside `~/dvconf-daemons` /
`~/dvconf-client`. Because `node_modules` + the mediasoup build are already present, a pull +
incremental install is fast (no native rebuild unless mediasoup version changes).

## 4. How this image was built (for reproducing / re-baking later)

1. **Enhance** (make universal): scp a git bundle of client `feat/relay-saturation-internet-bench`
   @ `d7a622c` → clone into `~/dvconf-client` + pin `packageManager=pnpm@10.30.3` +
   `pnpm install --frozen-lockfile`; then `npx playwright install --with-deps chromium` inside
   `~/dvconf-daemons`. (Enhancement completed successfully — image is universal.)
2. **Deprovision** (IRREVERSIBLE): `sudo waagent -deprovision+user -force` over SSH, then exit and
   never SSH in again (strips azureuser + machine identity).
3. **Generalize**: `az vm deallocate -g dvconf-rms-e2ee -n rms-r3-overlap`
   → `az vm generalize -g dvconf-rms-e2ee -n rms-r3-overlap`.
4. **Capture** into the persistent gallery:
   - `az group create -n dvconf-golden-rg -l koreacentral`
   - `az sig create -g dvconf-golden-rg --gallery-name dvconfGallery -l koreacentral`
   - `az sig image-definition create -g dvconf-golden-rg --gallery-name dvconfGallery \
       --gallery-image-definition dvconf-rms-golden --publisher dvconf --offer relay-saturation \
       --sku ubuntu2204-gen2 --os-type Linux --os-state Generalized --hyper-v-generation V2 \
       --features SecurityType=Standard -l koreacentral`  (⇒ no SecurityType feature = matches Standard source)
   - `az image create -g dvconf-golden-rg -n dvconf-rms-golden-2026-07-10 --source <r3 vm id> \
       -l japaneast --hyper-v-generation V2`  (japaneast managed-image bridge)
   - `az sig image-version create -g dvconf-golden-rg --gallery-name dvconfGallery \
       --gallery-image-definition dvconf-rms-golden --gallery-image-version 2026.07.10 \
       --managed-image <managed image id> --target-regions "japaneast=1" "koreacentral=1" \
       -l japaneast`  (source location = managed-image region; replicates to both)

> **Gotcha (learned this bake):** sourcing a SIG version directly from a VM (`--virtual-machine`)
> requires the VM and the version's `--location` to be the SAME region. r3 was japaneast, gallery
> koreacentral → the direct call failed `NotFound`/`InvalidResourceLocation` and left a phantom
> Failed version that had to be deleted. The fix was the japaneast managed-image intermediary with
> the version `--location japaneast`, then `koreacentral=1` in `--target-regions` for the cross-
> region replica.

### Cross-region copy recipe (if you ever only have the japaneast managed image)

To get the managed image usable in koreacentral without the SIG, either (a) use the SIG version
above (already both regions — preferred), or (b) create a new SIG version from the managed image
targeting the region you need (same command as step 4's last bullet), or (c) snapshot the managed
image's OS disk, copy the snapshot to koreacentral, and create a koreacentral image from it.

## 5. Add a newer image version later (keep the gallery, bump the version)

When code/deps drift enough to warrant a fresh bake, repeat steps 1-3 on a throwaway VM built
FROM this image (fast — deps already there; just `git pull` + rebuild if needed), then add a new
version to the SAME definition:

```bash
az sig image-version create -g dvconf-golden-rg --gallery-name dvconfGallery \
  --gallery-image-definition dvconf-rms-golden --gallery-image-version 2026.MM.DD \
  --managed-image <new managed image id> --target-regions "japaneast=1" "koreacentral=1" -l japaneast
```

`az vm create --image <definition id>` (no version suffix) always picks the newest version.
